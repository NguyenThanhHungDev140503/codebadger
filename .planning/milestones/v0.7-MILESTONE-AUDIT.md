## 3. Cross-Phase Integration & E2E Flow Verification

1. **Ingest to CPG Lifecycle Flow (Phase 5 → Phase 6):**
   - User registers remote repository via `POST /projects` or `project_create`.
   - `POST /projects/{id}/sync` fetches commit SHA, digests tree, and creates immutable `ProjectVersion`.
   - Version build is enqueued into `cpg_queue` with status tracking (`queued` → `building` → `ready`).
2. **CPG to Retrieval Flow (Phase 6 → Phase 7):**
   - Once build reaches `ready`, query executor connects CPG artifact.
   - `GET /versions/{id}/context?query=...` or `version_context` retrieves exact symbol definitions, callers, and citations with byte/item limits.
3. **Security & Governance Layer (Phase 8):**
   - `AuthMiddleware` verifies JWT Bearer tokens across REST routes.
   - Cross-tenant requests return 404 fail-closed.
   - Quotas enforce `MAX_PAYLOAD_SIZE_BYTES` (50MB) and `MAX_CONCURRENT_BUILDS_PER_TENANT` (2 concurrent).
   - `CorrelationMiddleware` attaches `X-Correlation-ID` to all responses and feeds `AuditLogger` structured JSON output.
   - `ErrorSanitizerMiddleware` hides internal database/file paths from clients.

## Re-audit — 2026-09-26

**Current result: GAPS FOUND.** This re-audit supersedes the 2026-09-08 readiness conclusion for current-code/runtime confidence; the original result above is retained as the historical record. No test suite or live MCP request was run during this re-audit.

### Verified integration gaps

| Requirement(s) | Finding | Current evidence |
|---|---|---|
| API-03 | MCP transport authentication does not bind tool authorization to the authenticated tenant. Public lifecycle tools accept caller-controlled `owner_scope` and pass it directly to `ProjectVersionService`; they do not read the verified user claims. | `src/api/auth_middleware.py` places claims on the HTTP request, while `src/tools/lifecycle_tools.py` exposes `owner_scope` on project, version, and context tools. |
| CTX-01–CTX-05, API-03 | The production lifespan does not construct or register `context_service`. REST returns 503 when it is missing; the MCP context tool raises “Context service not available”. | `main.py` registers lifecycle services and calls `register_lifecycle_tools()` without adding `context_service`; `src/api/rest_routes.py:get_version_context` and `src/tools/lifecycle_tools.py:version_context` both fail closed on the missing service. |
| API-03 | The prior MCP “parity” integration test does not exercise MCP calls with a tenant token. It checks `ProjectVersionService` directly with explicit owner scopes, so it cannot prove token-to-tenant binding. | `tests/integration/test_security_parity.py:test_cross_tenant_isolation_parity` tests REST with auth tokens, then calls service methods directly for the purported MCP portion. Its fixture manually injects `context_service`, masking the production wiring gap. |

### Verification record limitations

- Phases 5–8 have no `*-VERIFICATION.md` files. Phase 8 has a `08-VALIDATION.md`, but it repeats the MCP isolation claim without an authenticated MCP tool call.
- Archived plan summaries do not provide a consistent machine-readable `requirements-completed` frontmatter for the required three-source coverage check.
- The “130 tests passing” figure is from the prior dated report and was not rerun in this re-audit.

### Re-audit conclusion

The ingestion, version catalog, CPG lifecycle, and context service implementations have focused tests and remain reasonable candidates for staged testing. However, v0.7 cannot currently be considered fully verified end-to-end: MCP tenant authorization is not established, and public context retrieval is unavailable through the production service registry. Test the existing REST lifecycle and the pre-existing core CPG analysis flow first. Defer MCP cross-tenant authorization and live context retrieval acceptance until those integration gaps are fixed and verified.
